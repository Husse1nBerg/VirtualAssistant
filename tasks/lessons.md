## [2026-09-23] Prompt-only fixes can't solve STT-layer turn-cutting
**What happened**: Real call recording (analyzed via Deepgram batch transcription with diarization + word timing — CallLog 1a191858) showed Sky repeating an identical question verbatim within ~9s of first asking it, with no real gap for the caller's actual reply, and self-interrupting mid-sentence into a near-duplicate question. Earlier prompt edits (INTERRUPTIONS section, NEVER ASK TWICE, no-repeat rules) did not fix this.
**Root cause**: `agent.listen.provider` uses plain `nova-3` (v1), which exposes NO end-of-turn/VAD tuning in the Deepgram Agent Settings API — turn-finalization timing is an internal Deepgram default we cannot adjust. A turn can be cut/finalized at the AUDIO layer before the LLM ever sees the caller's full utterance, so no prompt instruction can fix it.
**Rule**: For "agent cuts off / repeats / mishandles silence" reports, check the STT/turn-detection layer (real recording + timing) before assuming it's a prompt problem. Deepgram's `flux-general-en` / `flux-general-multi` (v2) exposes `eot_threshold` (0.5-1.0, default 0.7), `eager_eot_threshold` (0.3-0.9), and `eot_timeout_ms` (500-60000, default 5000) for exactly this. `flux-general-multi` supports French via `language_hints`.
**Example**: `agent.listen.provider = { type:'deepgram', version:'v2', model:'flux-general-en', eot_threshold:0.8, eot_timeout_ms:7000 }`. Diagnostic: `curl -X POST "https://api.deepgram.com/v1/listen?model=nova-3&utterances=true&diarize=true" -d '{"url":"<recording-proxy-url>"}'`, then diff gaps between consecutive utterances.

## [2026-09-23] Over-confirmation is a separate, prompt-level bug from turn-cutting
**What happened**: Same call — after getting "car insurance" as a clear, complete reason, Sky recapped ("So you're calling about car insurance") then asked "Anything specific you'd like me to mention?" instead of moving to close. She also recapped after nearly every single answer (company name, reason, callback number) rather than once at the end.
**Root cause**: The prompt's CLOSING rule only specifies ONE end-of-call summary, but nothing told the model NOT to reflect back after every fragment, and "don't over-ask" (WHAT TO COLLECT) wasn't strong enough to stop probing for more detail once a short answer was already sufficient.
**Rule**: A short, on-topic answer to "what's the message" is complete — don't dig for more detail unless the caller volunteers it. Reflect back what was heard ONLY at the final close, not after each individual answer.
**Example**: Added NO MID-CALL RECAPS + STOP PROBING WHEN YOU HAVE ENOUGH sections to AGENT_INSTRUCTIONS in agentPrompt.ts.

## [2026-09-23] English-only STT silently drops an unknown caller's French opener
**What happened**: A second bad-call recording (CallLog e2c61e37, pre-Flux-fix) showed a caller opening with "Oui, bonjour." — completely absent from my diagnostic transcript on the first (English-only nova-3) pass, and (more importantly) absent from the LIVE agent's transcript too, since production used the same English-only STT for unknown callers at the time. The agent perceived silence after its own greeting, triggered a "checking in" filler ("Hello? Hi there."), the caller then re-tried in English sounding confused, and the agent additionally cut into a later mid-sentence pause — compounding into a multi-turn "interrupting/resetting" loop the user described directly.
**Root cause**: French support was previously gated entirely on `contact.language === 'fr'` (a known DB contact) — an unknown caller speaking French first had no recognition path at all. Diagnostic tooling made the same mistake (transcribing with `model=nova-3` and no `language` param).
**Rule**: STT recognition should not be English-only for anyone — Montreal is bilingual and unknown callers include French speakers. When diagnosing a call, always re-transcribe with `language=multi` (or the STT config actually used in prod) before concluding what was or wasn't said.
**Example**: Already covered by the 2026-09-23 Flux migration above — `flux-general-multi` with bilingual `language_hints` applies to ALL callers, not just known French contacts, so this class of silent-drop should no longer occur. Confirm with a live test call where an unknown caller opens in French.

## [2026-09-23] LLM invented a caller's name under uncertain audio
**What happened**: Same recording — Sky said "Hi, Dan. How can I help with Milo's appointment?" at 22s, before the caller had given ANY name (the real name, "Sylvia," wasn't given until 65s, and Sky properly asked for it then — never reconciling the earlier wrong one). A separate moment in the same call ("Alexa is saying no," inserted mid-sentence with no referent) looks like the same failure family — fabricated content appearing under uncertain/garbled input, rather than admitting uncertainty.
**Root cause**: The existing "never invent information" rule (WHAT YOU MUST NEVER DO) was too generic/buried to stop this in practice — nothing specifically told the model what to do when a name is unclear (ask vs. guess).
**Rule**: When audio is unclear, ask or say so — never fabricate a plausible-sounding name or detail to fill the gap.
**Example**: Added NEVER GUESS A NAME section to AGENT_INSTRUCTIONS (agentPrompt.ts), right after CALLER INTRODUCES THEMSELVES FIRST.

## [2026-10-08] Shipped a Deepgram Settings change without probing the real Agent API — broke every call
**What happened**: After the Flux STT migration (fb0544d), production greeted callers then went completely silent. `/health` showed 0 errors for 13 days. A direct WebSocket probe with the live `buildAgentSettings()` payload returned `INVALID_SETTINGS: "Cannot specify agent.language when using the Deepgram V2 (Flux) listen API."` The old nova-3 payload got `SettingsApplied`. We kept sending the top-level `agent.language` field next to the new v2 listen config, so Deepgram rejected the entire Settings message on every call and the agent never processed audio. The pre-connect greeting is a separate TTS clip, so it still played — making the failure look like "the agent is ignoring me" rather than "the agent never started."
**Root cause**: (1) A Settings-payload change was merged with "not yet verified with a live test call" written in todo.md — known-unverified, shipped anyway. (2) The `Error` event handler in callOrchestrator only `log.error`s; it never touches the health error counter, so health stayed green while 100% of calls failed.
**Rule**: Any change to the agent Settings payload (`baseSettings`, `buildAgentSettings*`, `buildCommandAgentSettings*`) MUST pass `npx tsx scripts/verify-agent-settings.ts` (real WS probe, exits 1 on rejection) before merge. Treat "flagged for later verification" on a prod-config change as a blocker, not a note. Agent `Error` events must be surfaced (health counter / alert), not just logged.
**Example**: `scripts/verify-agent-settings.ts` probes every builder and fails on any `Error` event. The fix: remove `agent.language` everywhere — French is fully covered by `language_hints`, `getTtsModel`, and the LANGUAGE OVERRIDE prompt block.

## [2026-10-09] "SMS with audio arrives late" was Twilio backing off on our media proxy, not our pipeline
**What happened**: Owner reported the combined transcript + recording MMS arriving much later than before. Twilio API timestamps (call `endTime`, recording `dateUpdated`, message `dateCreated`/`dateSent`, and the message's `media[].dateCreated`) showed our side creates the message 4–5s after hang-up every time, but on some calls Twilio only fetched the media 54s / 4min / 11min later and sent seconds after that. Fast calls had media fetched the same second the message was created.
**Root cause**: Twilio pulls the mp3 from `/voice/recording/:id` after `messages.create`. That proxy did a synchronous full download of a *fresh* recording (mp3 transcoded on demand) before answering; when that first pull was slow Twilio abandoned it and retried on a backoff schedule. No Twilio alert is raised for this (the 63007 alerts on every call are the WhatsApp send failing — unrelated). Previously the text and the audio were separate messages, so the text arrived in 4s and the slow audio went unnoticed; merging them made the media latency gate the whole notification.
**Rule**: When an MMS is "slow", compare `message.dateCreated` vs `media[].dateCreated` vs `dateSent` from the Twilio API before touching code — it tells you whether the delay is ours, Twilio's media fetch, or the carrier. Never make Twilio's media fetch depend on a slow upstream: have the bytes in memory before `messages.create`.
**Example**: `src/services/recordingCache.ts` — `prefetchRecording()` in the recording-status webhook (after acking Twilio with 200), `getCachedRecording()` in the proxy with live fetch as fallback.

## [2026-10-13] A pinned `value:` in render.yaml silently overwrote a dashboard env change
**What happened**: Owner switched `TTS_PROVIDER` to `elevenlabs` in the Render dashboard. The next deploy (which touched render.yaml) ran with `deepgram` again, and we only noticed by comparing mp3 bitrates of the greeting audio. Two deploy cycles were lost to it.
**Root cause**: render.yaml declared `TTS_PROVIDER` with `value: deepgram`. Render re-applies pinned Blueprint values on every Blueprint sync, so the dashboard edit was reverted. Nothing in the app could show which value it booted with.
**Rule**: Any env var the owner is expected to flip in the dashboard must be `sync: false` in render.yaml, never a pinned `value:`. Expose runtime-selected providers/modes in `/health` so "did the setting take?" is one request, not an audio forensics exercise.
**Example**: `/health` now returns `tts: { provider, elevenLabsKeySet }`. Also learned: ElevenLabs community *library* voices (like Siren, eXpIbVcVbLo8ZJQDlDnl) return 402 `paid_plan_required` on the free tier — premade voices work free, library voices need credits or Creator.

## [2026-10-16] Agent spoke spelled-out gibberish mid-call on the ElevenLabs bridge
**What happened**: First real call on ElevenLabs (CallLog 30befd86, 19.6–23.5s in the recording): the agent said "I didn't, like, g a, g g a. I…" and then restarted with the real sentence "I didn't quite catch that. Could you repeat it for me?". The LLM text for that turn (ConversationText / SMS transcript) was only the clean sentence, so the garbage came from TTS, not the model.
**Root cause**: We sent `model_id: eleven_flash_v2_5` to Deepgram's ElevenLabs websocket bridge. Deepgram's Voice Agent reference enumerates only `eleven_turbo_v2_5`, `eleven_multilingual_v2`, `eleven_monolingual_v1` ("we support Turbo 2.5 ... for low latency"); Flash is accepted but undocumented there, and Flash is the model most prone to hallucinating letters/syllables when fed a fragment of text, which is exactly what Deepgram does (ConversationText chunks split mid-word, e.g. "Huss" / "ein's").
**Rule**: For BYO TTS through Deepgram, use only a model_id the Deepgram reference enumerates. When a caller hears words that are not in the agent transcript, diff the recording (Deepgram batch, diarize + utterances) against the ConversationText lines first — audio-only text means the TTS layer.
**Example**: `ELEVENLABS_MODEL_ID = 'eleven_turbo_v2_5'` (same 0.5 credit/char). Forensic: transcribe `Recordings/<sid>.mp3` with `model=nova-3&language=multi&diarize=true&utterances=true` and look for agent utterances with confidence < 0.8.

## [2026-10-18] The "TTS gibberish" was aborted replies leaking through Twilio's buffer
**What happened**: After switching ElevenLabs to turbo v2.5 the owner still heard gibberish (call CA62505c4f…, Oct 18). Splitting the recording by channel (`.wav?RequestedChannels=2`, Deepgram `multichannel=true`) showed every garbled agent fragment ("Yeah. Got", "C. Hi", and Oct 16's "g a, g g a") played *while the caller was talking*, followed by the real sentence. The LLM transcript never contained the fragments.
**Root cause**: `handleAgentEvent` ignored `UserStartedSpeaking`. Deepgram aborts the agent's reply on barge-in, but audio already forwarded sat in Twilio's buffer and kept playing. Aura delivered whole sentences fast, so leaks sounded like normal speech; ElevenLabs streams in small chunks, so the leaked tail of an aborted reply is clipped syllables. The turbo model swap was a misdiagnosis: I blamed the model from one mixed-channel recording without checking overlap with caller speech.
**Rule**: Diagnose agent audio from the agent channel alone, and check whether bad audio overlaps caller speech before blaming TTS. Any Twilio↔Deepgram bridge must send `{event:'clear', streamSid}` on `UserStartedSpeaking` (Deepgram's Twilio guide, Step 6).
**Example**: `tests/bargeIn.test.ts`. Forensic: transcribe the 2-channel wav, list agent-channel words with confidence < 0.8, compare their times against caller-channel utterances.

## [2026-10-20] My barge-in audio gate muted Sky for an entire call
**What happened**: Call CAcff767c7 (Oct 20): greeting played, then silence for 37s. The SMS transcript shows Sky generated four replies; the agent channel of the recording contains none of them. The caller asked "Are you still there?" and hung up.
**Root cause**: Commit 104bd99 (#9) dropped all agent audio from `UserStartedSpeaking` until `AgentStartedSpeaking`. I shipped it assuming `AgentStartedSpeaking` arrives before each reply's audio; Deepgram's docs never state that, I knew it, and shipped anyway. On this call the gate never reopened, so every reply was discarded. Tests passed because they encoded my assumption, not Deepgram's behavior.
**Rule**: Never gate or drop the agent's audio on an event whose ordering isn't documented or observed in a real call log. Anything that can silence the agent needs live evidence first, and must fail open: a missed event must never mean permanent silence.
**Example**: Reverted #9. `UserStartedSpeaking` and `AgentStartedSpeaking` now log at info, so the next call's Render log shows the real event order before any further barge-in change.
